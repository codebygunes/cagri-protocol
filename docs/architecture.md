# Çağrı Protocol - Architectural Design: WebRTC-Based Decentralized Execution & Serving

## 1. General Workflow Architecture
1. **Bootstrap / Signaling:** Two browsers (peers) cannot discover each other directly. A lightweight WebSocket signaling server is utilized to establish the initial routing bridge.
2. **Offer / Answer Exchange:** Peer A (Host/Seed) connects to the Signaling server to initiate a secure routing room. When Peer B (Client) joins, WebRTC SDP (Session Description Protocol) and ICE Candidate exchanges are tunneled through this server.
3. **P2P Direct Connection:** Once signaling is complete, the WebSocket connection can be terminated or kept strictly as a fallback. Data transmission occurs entirely peer-to-peer (browser-to-browser) via the **`RTCDataChannel`**.

## 2. Secure File Chunking and Assembly Logic
* **Packaging (Chunking):** Static assets (HTML/JS/Images) or execution payloads are converted into binary (`ArrayBuffer`) formats and fragmented into deterministic chunks (e.g., 16KB each). Each chunk is securely tagged with an index number, metadata, and expected cryptographic hashes.
* **Transmission:** These chunks are streamed sequentially or on a request-driven basis over the `RTCDataChannel`.
* **Assembly & Execution:** The receiving peer (Client) accumulates the verified incoming chunks into memory arrays. Once all chunks are successfully received and their integrity is strictly validated against the manifest, they are converted into a `Blob` object and securely rendered or executed within the browser's sandbox.

## 3. Cryptographic Security & Privacy Layer
* **Zero-Knowledge Proofs (ZKP):** Peer authentication and network access are verified via zk-SNARKs, allowing nodes to prove their legitimacy without exposing IP addresses or sensitive session tokens.
* **Post-Quantum Cryptography (PQC):** Data chunks and state transitions are signed using Lattice-based quantum-resistant algorithms, future-proofing the network against advanced cryptographic threats and downgrade attacks.

## 4. Off-Chain Execution & Ecosystem Integration
* **In-Browser WASM VM:** Assembled payloads can include WebAssembly smart contracts that execute securely within the browser's sandbox. State changes are hashed and verified across the P2P mesh network.
* **Polkadot/Substrate Settlement:** The protocol acts as an off-chain execution layer. Finalized state roots and critical consensus proofs generated by the WASM VM are periodically anchored to the Polkadot/Substrate chain for absolute finality.
* **Incentive Mechanism:** Peers seeding data and maintaining network uptime are dynamically rewarded with reputation points and verifiable badges, preventing Sybil attacks and ensuring network resilience.
